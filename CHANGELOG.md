## [0.1.0-rc.10] - 2026-11-27

First release. The program is early: the file format, the command line and the JSON outputs may still change before 1.0 (see [docs/versioning.md](docs/versioning.md)), and the library `oxispec-core` has no stability promise yet.

### Added

- **The graph.** Nodes as markdown with YAML front matter, typed links with computed reverse links, scenario IDs, and structural checks (`init`, `modules`, `new`, `link`, `check`, `show`). Modules and presets choose what a project uses. A local index with content hashing, and a text index for `search`.
- **History.** `--at` on `show`, `check` and other commands, `history`, `diff`, `rollback`, `tag`, and `check --changed`.
- **Change and release.** Change sets with a lifecycle and a recorded approval, tasks under `## Tasks` (progress in `show` and `change list`, `change task done` and `undo`, the tasks that name a requirement in `show`, and warnings W027 and W028), and `release prepare`, `check`, `publish` and `list` with generated notes, a suggested SemVer bump and gates.
- **CI.** `oxispec ci` reports only the findings a change introduces, with SARIF, JUnit and pull request comment output. `oxispec site` builds a static site, with a version picker for releases.
- **Trace.** `spec:` and `verifies:` comments in any language, coverage, suspect links bound with tree-sitter for Rust, Go, TypeScript and JavaScript, `confirm`, test result import (JUnit XML, `go test -json`), and a setting for the languages that are scanned.
- **Projects with their own ID shapes.** `trace.test_ids` finds tests by an ID in their title (`it('TC-CAT-001 lists programs')`), and `trace` lists the tests of a node that has no scenarios. `ids:` names IDs of a project's own shape that need no node (a link to one is not dangling, `trace` lists where it is named), `external:` does the same for the keys of another system such as Jira, with a link only when the config gives a URL with `{id}`, and a range such as `TC-CAT-1200..1212` is read in test titles and links as the IDs it stands for. `sources:` reads the rows of a table or the headings with an ID in existing documents as read-only nodes (type, title, links, fields, the line), with a history of their own, `diff` and `--at`, suspect links and a page each in the site; `link`, `set-status` and `rollback` refuse them. W030 warns about a row with no ID. W002 now says the line of a front matter that is not valid YAML, and that a value with a colon needs quotes.
- **Consistency.** Claims and a vocabulary with an exact solver that reports conflicts with the smallest set of claims. State machines with property checks, counterexample paths, Mermaid diagrams and generated tests. An architecture model (C4 and deployment) with Mermaid views and `forbid` rules, in the format of a profile (`c4-person`, `c4-system`, `c4-container`, `c4-component`, `c4-environment`; `new architecture --format`). W029 warns when the requirements of one ID domain are in more than one folder. A PRD, a test plan, a risk and a tech debt item have profiles too (`one-pager`, `ieee-829`, `treatment-plan`, `principal-and-interest`), chosen with `--format` on `new` or in the config; a profile sets the sections only.
- **Entities.** A node type for the things the specs are about, with typed attributes that claims can use. `oxispec entities` shows what depends on one, `ci` says what a change to one touches and whether it can break a reader, the code that represents it is linked with a `spec:` comment and checked for a field for each attribute, and the nodes about an entity are to review when it changes.
- **Records of work.** Tech debt, a risk register, test plans read against the tests, and product requirements documents, each a node type with checks, a command and a release gate where it fits.
- **Names.** A node can list `aliases`, such as the ID it had in another tool; a link, a `spec:` or `verifies:` marker, `show`, `trace` and `search` that use one read as the node itself (E042 reports an alias that is taken). `oxispec list` lists nodes by type, status and domain, `show --text` prints the text of a node, and `oxispec read NAME` prints the whole specification of one functionality (the folder of its requirements or the domain of their IDs): every requirement with its scenarios and the change sets still open for it.
- **Formats and import.** Format profiles, ADR formats (MADR, Nygard, Y-statement) with `adr convert` and `import adr`, requirement styles (EARS, user stories, Gherkin), compliance profiles, and `import specs` from OpenSpec, Spec Kit, Kiro, plain markdown, a PRD and an OpenAPI description, with a plan that can be looked at and changed first (`--only`, `set --where`). A requirement is a node of its own, an OpenSpec or markdown requirement keeps the ID of its source (`CAR-1` gives `REQ-CAR-1` with that alias), and `--status` sets the status the requirements start with. `import plan start --include-archive` makes each archived OpenSpec change a `merged` change set, approved by the archive and dated by its folder. `domains:` in the config chooses the domain of imported IDs, by the name of a spec or by the prefix of a source ID. The hyphens of a spec's name stay in its folder and domain (`account-and-profile` gives `REQ-ACCOUNT-AND-PROFILE-0001`). `oxispec set-status accepted --domain NAME` sets the status of requirements, for example to accept what an import brought in as drafts.
- **Where the documents are.** `docs_dir` in the config is the folder of the documents, and `oxispec init --docs-dir DIR` sets it. A new project uses `oxispec/` (the architecture model is in `oxispec/architecture`); a config without the key still means `specs`. `oxispec move-docs DIR` moves the documents to another folder at any time and sets `docs_dir`: it reports whether the new folder exists and what is in it, shows each folder as `can move` or `CLASH`, names the folders to rename when something clashes, and moves all or nothing. `--dry-run` writes nothing.
- **Documents of a project.** `oxispec onboard` fixes the kinds of documents a project keeps and the format of each (`--docs type[:format],…`, `--yes`, `--show`, or questions on the terminal); they are written to `documents:` and `formats:` in the config, and `new` then needs no question and refuses a kind that is not on the list.
- **Products and platforms.** A folder with its own `.oxispec/config.yaml` below the project is a product: it is left out of the parent graph, checked with its own config, listed by `oxispec products`, and shown in one site with a product picker. A link `product:ID` names a node of another product; it is checked in the other project, `show` and `ci` report the nodes of other products that link into a change, and the site links to them. With `--at`, the link is read against the other project as it was at that revision. From the top project, `list`, `read`, `search` and `show` take `--product PATH` to read one product; `list` and `search` take `--all-products` and name each node of a product `product:ID`; `show` and `read` find a node or a functionality that only one product has.
- **APIs.** Requirements titled as calls are the operations of an API. `docs openapi` writes an OpenAPI skeleton and compares a file or a running service with the requirements, `api show` gives the card of an operation, and `api index` and `api search` find an operation by meaning with a built-in embedder or an embedding service on your machine.
- **Agents.** Skills for Claude Code, Cursor, GitHub Copilot and Gemini CLI, with `agents update`, `check` and `export`. An MCP server (`oxispec mcp`) with tools, resources, prompts and context packs, `oxispec serve` for many clients over HTTP with limited tokens and an audit log, and `oxispec connect` to write the server into each client's config.
- **Documentation.** A user guide, a command reference, a table of check codes and an MCP tools reference written from the program, and runnable examples of the library.
- `oxispec status`, `oxispec token`, and `oxispec-stress` (a development tool for stress and load tests, not published).

### Fixed

- Concurrent searches, `new` and `link` no longer corrupt the index, repeat an ID or lose an edit.
- A byte order mark in a spec file is read, and a closed pipe no longer panics.
- `machine --tests` no longer runs out of memory on a large machine, and large projects check in seconds (see [docs/review.md](docs/review.md)).

### Known limits

- No hosted server, no sign-in (OIDC) and no database: the specs are files in git.
- The embedding service for `api search` must be reached over plain `http://`, and the built-in embedder matches words, not meaning.
- Claims and entities describe numbers, flags and choices, not free text. There is no check of requirements written in natural language.
- Entities and their code are compared by name, not by type.
- Releases are built for macOS (Apple silicon and Intel), Linux (x86_64 and arm64, glibc) and Windows (x86_64). The binaries are not signed.
